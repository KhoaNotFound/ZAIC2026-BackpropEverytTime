# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DataMate inference pipeline: Qwen3.5 (default `Qwen/Qwen3.5-9B`, NF4 4-bit, split across two Kaggle T4s) answers Vietnamese business questions by calling read-only data tools over per-business Excel/CSV/SQLite files, then emits typed JSON answers. Inference and evaluation only — no training, no weight updates. README.md is in Vietnamese and holds the full Kaggle runbook; AGENTS.md holds repo conventions.

## Commands

`inference.py` sets `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` before torch loads. Run from the repo root; there is no build step. The local dev machine (WSL) has no `python` on PATH and no project venv; `uv sync` would pull torch/CUDA wheels. For CPU-only testing use an isolated uv env:

```bash
UVX="uv run --no-project --isolated --with pytest --with pandas --with openpyxl --with duckdb --with ruff"
$UVX python -m pytest -q                              # 46 pass; torch-based tests skip
# With CPU torch the prefix-cache equivalence test also runs (only the 2-GPU split test skips):
uv run --no-project --isolated --index https://download.pytorch.org/whl/cpu --index-strategy unsafe-best-match --with torch --with "transformers>=5.13" --with accelerate --with pytest --with pandas --with openpyxl --with duckdb python -m pytest -q
$UVX python -m pytest -q tests/test_pipeline.py::test_agent_end_to_end_without_gold   # single test
$UVX ruff check zaic inference.py evaluate.py tests

# The commands below are written for Kaggle; locally, prefix with uv as above (or use python3)
# Validate inputs/sampling without loading weights
python inference.py --data-dir data/train --limit 5 --dry-run
# Real run (needs CUDA; --device-map split needs >=2 GPUs; use cuda:0/auto for one)
python inference.py --data-dir data/train --limit 1 --output outputs/smoke/predictions.jsonl
# Custom question (needs --business-id and --as-of-date)
python inference.py --data-dir data/train --business-id biz_123 --as-of-date 2026-06-28 --question "..." --output outputs/custom/predictions.jsonl
# Score (default --scope run reads selected IDs from predictions.run.json; use --scope predictions|all otherwise)
python evaluate.py --predictions outputs/predictions.jsonl --answers data/train/answers.jsonl --questions data/train/questions.jsonl
```

Inference CLI defaults: `--limit 20` (0 = all), `--sampling stratified` (round robin over shuffled businesses; also `random`, `first`), `--seed 42`, `--max-steps 16`, `--context-tokens 32768`, `--max-new-tokens 2048`, `--temperature 0.7 --top-p 0.8 --top-k 20 --repetition-penalty 1.0` (0 = greedy), `--quantization 4bit` (`8bit`, `none`), `--thinking` off, `--output outputs/predictions.jsonl`.

`data/`, `outputs/`, `reports/` are gitignored. Local splits: `data/train` (has `answers.jsonl`) and `data/public_test` (no answers). Split layout: `{questions.jsonl, answers.jsonl?, rulebook.md, calendar.csv, data/<business_id>/...}`; each business dir must have its own `README.md` (inference validates it up front). Questions are `{id, business_id, question, as_of_date}`, mostly in informal Vietnamese. `scripts/analyze_data.py` profiles the dataset into `reports/` using only the standard library.

## Architecture

Flow: `inference.py` (CLI, sampling, checkpointing) → `zaic.agent.answer_question` (per-question loop) → `HFBackend.generate` (`zaic/model.py`) and `Tools.call` (`zaic/tools.py`), with parsing/validation in `zaic/formats.py`. `evaluate.py` scores independently.

- **Custom action-JSON protocol, not Qwen native tool calls.** The `SYSTEM` prompt in `agent.py` plus `TOOL_HELP` in `tools.py` define it. Each model turn must be one JSON object: `{"action":"tool","name":...,"arguments":{...}}`, a flat form `{"action":"<tool_name>", ...params}`, or `{"action":"final","type":...,"answer":...}`. `formats.parse_action` takes the first complete top-level JSON object (prose around it is ignored; truncated output never parses). `formats.normalize_action` canonicalizes both tool forms against `TOOL_PARAMS` (whitelist + per-tool required/optional params; unknown keys dropped, params beside `arguments` merged, conflicts and missing required params raise `ProtocolError`; in the flat form `name` is the load_table *table name*, not the tool). The normalized action replaces the raw assistant message in history so malformed calls aren't reinforced; the raw text stays in the trace. Changing the protocol means updating the SYSTEM prompt, `TOOL_HELP`, `normalize_action`, and the parametrized tests in `test_pipeline.py` together.
- **Agent loop guards** (`agent.py`): the prompt is one system message (SYSTEM + TOOL_HELP + rulebook, identical for every question so the backend can reuse its prefix) plus one user message (business README, file lists, question, step budget); each step appends the normalized action (or the invalid reply shortened to 600 chars) and one feedback message. Feedback is typed: tool result, SQL error with loaded tables/columns (`Tools.describe_tables`), path error with the file list, protocol error, or rejected final with the expected format. Non-abstain finals need a successful *data* tool (`EVIDENCE_TOOLS`; `list_files` does not count) and must pass `formats.valid_answer` (types: number, percent, string, date, boolean, list, table, unanswerable with optional string reason per rulebook §7, abstain). The prompt states the step budget and every feedback message ends with the actions left. On `ContextLimitError` the oldest full tool result is replaced by a stub and generation retried (`compactions` metric); only when nothing is left does the question end as `context_limit`. `HARNESS_VERSION` goes into `.run.json`; bump it when prompts/tools/loop rules change. A reply identical to the previous one gets a warning and is not re-executed; a third identical reply in a row → status `stalled` (prediction stays abstain). Exhausting `max_steps` → `max_steps`. Exceptions → `error` with traceback. Oversized tool output is replaced with a JSON truncation envelope.
- **Tools / data isolation** (`tools.py`): `Tools.resolve` restricts paths to `data/<business_id>/` plus split-level `rulebook.md`/`calendar.csv`, and only `.md/.xlsx/.csv/.sqlite`. `answers.jsonl` must never be reachable by any tool or prompt (tests assert "SECRET LABEL" never appears in prompts). Excel/CSV go through one reader (`Tools.read_rows` + `cell_text`) so `inspect_table` previews show exactly the text SQL sees, with the same zero-based row numbers; `inspect_table` lists every sheet with real row counts and previews as many sheets as fit (~6k chars), optional `sheet`. `load_table` accepts one sheet, a list, or `"*"` (stacked, columns matched by header name, warning if headers differ), stores cells as text with blanks as NULL, skips fully blank rows, and adds `_row` (source row index) and `_sheet` (Excel) so rulebook §8 group fill-down/dedup can be done in SQL (no fill-forward/dedup by the tool); tables persist across steps within one question only (a fresh `Tools` per question). `run_sql` is single-statement SELECT on DuckDB with `enable_external_access=False`, 2 threads, 2GB memory and a 30s interrupt timer; `query_sqlite` is read-only with an authorizer and timeout. Results capped at 100 rows. No arbitrary Python execution by design.
- **Model backend** (`model.py`): imports torch/transformers lazily so CLI, evaluator, and tests run without GPU deps. Model-agnostic `HFBackend`: `model_class` picks text-only `Qwen3_5ForCausalLM` for Qwen3.5 (requires transformers >=5.13) and `AutoModelForCausalLM` otherwise; `chat_text` folds the system prompt into the first user turn if a template rejects the system role. Swapping the LLM is just `--model` (plus its recommended sampling flags). `make_split_map` builds an explicit device map placing whole decoder blocks contiguously across GPUs (embeddings and `lm_head` on GPU 0, final norm on last GPU). Generation samples with the Qwen non-thinking preset (seeded per question via `inference.question_seed` → `HFBackend.set_seed`) and stops at the first complete JSON object (`make_json_stop`); prefix KV reuse via `PrefixCache` (snapshots at the end of the system message — which holds SYSTEM + TOOL_HELP + rulebook and is identical across questions — and at the end of the latest user message; deep-copied before each generate because hybrid linear-attention state cannot be cropped; a boundary is used only if re-tokenizing up to it reproduces the prompt tokens; any failure prints a warning and falls back to full prefill; `--no-prefix-cache` disables; `cached_tokens` metric), `logits_to_keep=1`, chunked prefill (`--prefill-chunk-size`, 0 disables). Raises before generating if input + `max_new_tokens` exceeds `--context-tokens`.
- **Run artifacts & resume** (`inference.py`): from `--output X.jsonl` it writes `X.run.json` (config, selected IDs, source hashes, versions), `X.traces.jsonl`, `X.metrics.jsonl`, `X.summary.json`. The predictions line is written *last* per question and acts as the commit marker. `--resume` requires an identical config/sample/source hashes; otherwise use a new output path (an existing output without `--resume` is refused). A runtime `error` stops the run with exit code 1 and disables time extrapolation.
- **Scoring** (`evaluate.py`): type must match; strings compare after NFC + casefold with whitespace/punctuation stripped (accents are *kept*), against gold plus `alias`, also accepting the name with a phone number before/after it (rulebook §9) (aliases apply to strings, list items by index, and the first table column); numbers need exact match within 1e-8 absolute (deliberately no relative tolerance, so large VND sums must be exact); lists are ordered; tables match columns by name (else position) and rows via bipartite matching; `unanswerable` scores on type only; a prediction whose `reason` is not a string counts as abstain (rulebook §7). Score = correct − incorrect; abstain is neutral. If `predictions.metrics.jsonl`/`.run.json` sit next to the predictions, the report also gets a `runtime` benchmark section (status counts, outcome by status, seconds/steps/tool calls/tokens stats, peak VRAM per GPU, load time).

All current work targets the `train` split (the only one with labels). The goal is a baseline of the pretrained, non-fine-tuned Qwen under the current harness; `notebooks/kaggle_inference.ipynb` drives it with `LIMIT`/`SEED` and derives the output dir from them.

## Testing approach

Tests use a synthetic dataset fixture (`source` in `tests/test_pipeline.py`, which plants `answers.jsonl` containing "SECRET LABEL") and a `ScriptedBackend` that replays canned model responses — extend these rather than loading a real model. `tests/test_gpu_smoke.py` builds a tiny random `Qwen3_5TextConfig` model (no download) and checks that split-map + chunked-prefill generation equals single-GPU output. They do not substitute for real Qwen runs on Kaggle; when reporting model changes, distinguish simulated tests from actual checkpoint runs and state hardware/config.

## Conventions

- Commit subjects are imperative ("Accept Qwen flat tool actions and stop repeated protocol loops").
- Keep protocol handling (`formats.py`), data access (`tools.py`), and model execution (`model.py`) in their own modules.
- Never commit datasets, weights, or traces (traces contain business/customer data).
